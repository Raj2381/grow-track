# Round 2 pipeline: predict, explain, recommend

> **The data is synthetic.** Every student, mark and outcome was generated by rules we designed (`data/DATASET.md`).
> The metrics below show that the pipeline is leakage-free and works end to end. They are **not** a claim about accuracy
> on real students. Retrain on the institution's own records before any decision is based on the output.

The app never runs Python. This pipeline turns `data/csv/` into static JSON that the dashboards read.

## Run it

```bash
npm run generate:data     # only if you change lib/dataset/ (regenerates data/csv)
npm run ml:all            # the whole pipeline, then every test (about 2.5 minutes)
npm run ml:all -- --check # runs the pipeline twice and proves all 14 output files are byte-identical (about 4.5 minutes)
npm run test:ml           # leakage, ML, what-if and recommendation tests only
```

Requires Python 3.9 with numpy, pandas, scikit-learn and scipy (nothing else; no SHAP, xgboost or matplotlib) and Node with `tsx`.
Outputs carry no timestamps or absolute paths, and every random choice uses seed 42.

## How leakage is prevented

1. Every table is cut to what was known at the end of semester N before anything else (`common.known_at`, the only place the rule lives).
2. The cut tables are **then** cleaned, so imputation medians use the past only. (Cleaning first and filtering second would leak: a student's median would include future semesters.)
3. Targets are joined last as separate `y_` columns; `archetype_diagnostic` is dropped before any feature exists; `gender` is never a model input.
4. Students, not rows, are split. Each student contributes three rows (N = 2, 3, 4), so a row-level split would leak. 20% of students (160) are held out and touched once.
5. `test_leakage.py` wrecks every record dated after N (numbers blown up, flags flipped, statuses scrambled) and asserts that the features for N do not move. It was itself tested: removing a time filter, or cleaning before filtering, makes it fail.
6. Interventions enter as the priority at creation, not the status, because the CSV stores only the final status.

## How to read `public/data/model-metrics.json`

Per outcome: `test_metrics` (held-out students; ROC-AUC with a 95% bootstrap interval over students), `baselines` (the Round 1 Success Score, the Round 1 risk flag, a flag-everyone baseline), `gain_over_success_score`, `ablation` (the same model trained **without** the Round 1 score), `by_semester`, `by_department`, `early_detection`, `fairness_out_of_sample`, `calibration` (reliability tables, Brier score), `global_drivers` (permutation importance).

The positive class is always the at-risk class. For placement it is **not ready**, so a student's chance of being ready is `1 - p`.

### Results on the held-out students

| Outcome | Model | ROC-AUC (95% CI) | Recall | Precision | Success Score AUC | Success Score recall / precision |
|---|---|---|---|---|---|---|
| SGPA below 6 | logistic | 0.905 (0.865-0.939) | 0.94 | 0.37 | 0.795 | 0.87 / 0.24 |
| Backlog risk | logistic | 0.928 (0.888-0.961) | 0.82 | 0.59 | 0.885 | 0.92 / 0.28 |
| Placement readiness | logistic | 0.939 (0.914-0.963) | 0.87 | 0.94 | 0.849 | 0.85 / 0.88 |
| Engagement drop | gradient boosting | 0.681 (0.622-0.736) | 0.80 | 0.21 | 0.436 | 0.93 / 0.15 |

Next-semester SGPA: MAE 0.59, RMSE 0.83, R2 0.71, against persistence (predict last SGPA) RMSE 1.04. The 80% prediction interval covers 81% of held-out cases.

**Read these honestly**

* The model beats the Success Score on AUC for every outcome, and removing the Round 1 features changes AUC by less than 0.01, so the gain does not come from the score.
* For **backlog risk** the operating points differ: the model flags fewer students (precision 0.59, recall 0.82) than the Success Score (precision 0.28, recall 0.92). The gain is precision. At the Success Score's own precision the model's recall is no higher (`delta_recall_at_fixed_precision` is 0.00).
* **Engagement drop** is the hardest outcome. The generator gives even stable students an 11-14% chance of a drop, so much of the label is irreducible noise; the model reaches AUC 0.68, and at recall 0.80 it flags about half the students (precision 0.21). The Success Score is no better than a coin flip there (0.44).
* The early-detection numbers for SGPA (6 rows) and backlog (5 rows) are far too small to mean anything. Placement (142) and engagement (36) are the usable ones.
* Faculty feedback is a strong driver of several outcomes. In the synthetic data faculty ratings are derived from the same latent effort that drives marks, so this is partly an artefact.

### Thresholds and risk levels

The screening threshold is the one with recall of at least 0.85 on out-of-fold training predictions (the brief asks for 0.80; the extra 0.05 is a margin because held-out recall moves by about five points with roughly 100 positives). On the held-out students recall was 0.94 / 0.82 / 0.87 / 0.80.

Because that threshold alone flags a third of the campus, risk levels have two tiers: **Medium** at or above the screening threshold, **High** at or above `min(0.90, max(screening, 2.5 x the outcome's base rate))`. Overall risk follows the brief: High if backlog risk is High or at least two outcomes are High. At the forecast cut-off about 20% of students are High, 32% Medium, 48% Low.

## Explanations

* Global drivers: permutation importance on the held-out students (20 repeats).
* Per-student drivers: contribution = logistic coefficient x standardized value, summed per **driver family** (attendance level, attendance trend, backlogs, and so on). Summing per family stops correlated measures from offsetting each other ("attendance fell" looking protective). The sum over families equals the model's decision function (verified to 1e-14).
* Only drivers that also agree with common-sense direction are shown as reasons; effects that run against it are offsets between correlated measures and stay inside the probability. Background features and the Round 1 score are never listed as reasons.
* For the engagement-drop outcome the forecast comes from gradient boosting, while the drivers explain the logistic model. The metrics file says so.

## What-if

`public/data/whatif-model.json` and `whatif-inputs.json` let `lib/whatif.ts` re-score a student in the browser after editing attendance, LMS logins, assignment submission, best mock-interview score or best coding score. An edit also moves the features computed from it (for example attendance moves the attendance trend and the success score); everything else is held fixed. It matches the Python probabilities to within 0.0005 (`scripts/test-whatif.ts`). It uses the logistic model, so for engagement drop it approximates the boosting forecast.

## Recommendations

`lib/recommendations.ts` holds a table of rules (placement bootcamp, attendance contract, backlog remedial or prevention, academic support, study skills, silent decliner, combined recovery, stretch opportunity) plus segment and department rules. Every recommendation carries the target, action, reason (with the student's own numbers, the forecast probability and the model's lead driver), owner, priority, due date and the outcome it should move. Priority scoring is documented at the top of the file and in `recommendations.json`. Students with an open semester-5 intervention covering the same theme get a follow-up on that plan rather than a duplicate.

## Known limitations

* Synthetic data; see the note at the top.
* One batch, so no year-on-year comparison and no cohort drift.
* The held-out set is 160 students, so every held-out figure has a wide interval.
* Calibration is cross-fit (fitted on out-of-fold predictions) rather than `CalibratedClassifierCV`, so thresholds and calibration come from the same honest predictions.
* Boosting uses a fixed iteration grid chosen by grouped cross-validation instead of sklearn's built-in early stopping, which would hold out random rows rather than whole students.
* numpy 2.0 with Apple's Accelerate library prints spurious "overflow in matmul" warnings on finite data; that exact message is silenced in `common.py` (verified against an element-wise recomputation).
