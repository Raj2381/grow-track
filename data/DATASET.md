# GrowTrack unified student dataset

> **This dataset is synthetic.** Every student, mark, attendance record and outcome was generated by
> `lib/dataset/generate.ts` from a fixed seed (20261009). It is not institutional data. The pipeline is real;
> the numbers must be replaced with the college's own records before any decision is based on them.

Regenerate with `npm run generate:data`. Prove determinism with `npm run generate:data -- --check`.

## 1. Size and calendar

| Item | Value |
|---|---|
| Students | 800 (ids `STU-0001` to `STU-0800`; `STU-0001` is the default demo student) |
| History | Semesters 1-5 complete, 6 subjects each (30 results per student) |
| Batch | One batch, admitted 2024. Everyone is in semester 5 (3rd year) |
| "Today" | 2027-01-08, just after the semester-5 results. Semester 6 is the upcoming semester to forecast |
| Departments | Computer Science 265, Information Technology 179, Electronics 175, Mechanical Engineering 108, Civil Engineering 73 |

Because there is a single batch, "year" is always 3rd year. Trends over time must use semesters.

## 4. Features and targets (leakage rules)

A training row is `(student_id, as_of_semester N)` with N = 2, 3, 4. **N = 5 is the upcoming semester: its targets are blank.**

| Kind | Columns | Rule |
|---|---|---|
| Features | every table except `outcomes` | Use a record only if its semester is <= N, or its date (`date`, `due_date`, `attempt_date`, `created_at`) is on or before the last day of semester N (see `SEM_DATES` in `lib/dataset/calendar.ts`) |
| Targets | `outcomes.csv`: `next_sgpa`, `next_sgpa_band`, `next_sgpa_below_6`, `new_backlog_next_sem`, `failed_to_clear_existing_backlog`, `backlog_risk_any`, `placement_ready_before_season`, `engagement_drop_next_weeks` | Look at semester N+1. Never use them, or anything derived from semester N+1, as a feature |
| Row context | `has_active_backlog_at_asof`, `label_available` | Known at N. `has_active_backlog_at_asof` is a legitimate feature |
| Diagnostic only | `students.archetype_diagnostic` | The hidden generator profile. **Do not train on it.** It exists to check the data, nothing else |

Pitfalls to avoid: `semester_results` holds **first-attempt** marks, so it is safe. Use `backlogs.csv` and the attempt
dates to know whether a backlog had been cleared by the end of semester N. `attendance_monthly` and `lms_monthly` for
semester N+1 are target material. `student-portal/data` JSON shows the **final** state (after supplementary exams) and
must not be used for time-travelled features.

### Target definitions

| Target | Definition |
|---|---|
| `next_sgpa` / `next_sgpa_band` | SGPA of semester N+1 (first attempt). Bands: Low < 5.5, Average < 7, Good < 8.5, Excellent |
| `next_sgpa_below_6` | SGPA of N+1 is below 6.0 |
| `new_backlog_next_sem` | at least one subject failed in semester N+1 |
| `failed_to_clear_existing_backlog` | student had an active backlog at the end of N and it is still active at the end of N+1. Blank if there was none |
| `backlog_risk_any` | new backlog **or** failed to clear an existing one |
| `placement_ready_before_season` | by the end of N+1: latest aptitude >= 60, best coding score (>= 5 questions) >= 60 and best mock interview >= 60, each with at least one attempt |
| `engagement_drop_next_weeks` | engagement index (50% attendance, 30% logins vs 27/month, 20% assignment submission) over the first two months of N+1 is at least 8 points below the last two months of N |

## 5. How the data is built

* Each student has a hidden latent profile (ability, consistency, employability focus, external risk) and one of nine
  archetypes. Every observed signal is derived from the profile plus noise, so features are correlated with outcomes
  without any single rule producing a label.
* Trends are baked in over semesters (attendance and LMS decay or grow), so slopes and drops are meaningful features.
* Outcomes are generated from the past state plus randomness, never copied from the Round 1 Success Score.
* Aptitude, coding and interview attempts are voluntary except one compulsory aptitude screening in semester 5, so every student has at least one aptitude score by then.
* Grading follows `student-portal/lib/scoring.ts`: pass = total >= 40 and external >= 24; O 90+, A+ 80+, A 70+, B+ 60+, B 50+, C 40+, F.
* Supplementary exams are held at the end of each later semester; a backlog from semester 5 has only its first attempt.

## 6. Data quality issues injected into the CSVs

The CSVs are deliberately dirty so that cleaning is a visible step. Missing values are empty cells.

| Table | Column | Issue | Cells affected |
|---|---|---|---|
| students | income_band | missing | 31 |
| students | entry_band | missing | 19 |
| semester_results | internal | missing | 220 |
| attendance_monthly | lectures_attended | missing | 1429 |
| attendance_monthly | lectures_attended | outlier | 339 |
| lms_monthly | avg_quiz_score | missing | 540 |
| lms_monthly | hours_online | missing | 408 |
| lms_monthly | logins | outlier | 76 |
| assignments | score | missing | 1061 |
| coding_attempts | time_taken_sec | missing | 111 |
| coding_attempts | score_percent | outlier | 9 |
| interview_attempts | confidence | missing | 47 |
| skill_assessments | score | outlier | 121 |

Outliers: attendance above lectures held, logins multiplied by 8, coding scores above 100, and skill scores of 250.
Suggested handling: impute missing values by the student's own median, cap attendance at lectures held, and clip scores to 0-100.

## 8. Known limitations

* **Synthetic data.** Relationships were designed by us, so a model can partly learn the generator's own rules. Report
  model metrics as evidence the pipeline works, not as a claim about real student behaviour.
* A single batch means no year-on-year comparison and no cohort drift.
* Placement outcomes are measured against fixed benchmarks, not real job offers.
* Engagement drop is a composite index defined here; a real deployment should agree the definition with faculty.
* The Success Score used as a baseline is time-travelled from history, because the portal's live score needs the final record.

## 9. Round 2 pipeline

The models, explanations, what-if view and recommendations built on this dataset live in `ml/` and `lib/recommendations.ts`.
Run `npm run ml:all`; read `ml/README.md` for the order, the leakage rules, the results and the limitations, and
`ml/FEATURES.md` for every feature definition. The pipeline rebuilds from `data/csv/`, so rerun it after `npm run generate:data`
changes the data.

## 10. Database

The same data is loaded into Supabase by `npm run db:seed` (history tables, built from the generator, not the messy CSVs) and
`npm run db:load-ml` (model outputs). See the "Database" section of the README for setup, roles and commands.
